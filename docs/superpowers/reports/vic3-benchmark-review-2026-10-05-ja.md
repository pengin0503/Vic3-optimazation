# Victoria 3 ベンチマーク初回解析（2026-10-05）

7条件すべてで HWiNFO と TickTask CSV を取得できている。重い処理の候補は確認できたが、最速の TaskThreadCount、Speed 5 の速度向上率、再現性は現資料から確定できない。各条件の実測所要秒数がなく、記録したフレーム範囲も一致しないためである。

## 確認した環境とユーザー補足

- `system.log`：Victoria 3 1.14.5 / game hash `9f8281a37e85639359b3b0c2c5df0196e975ca4b`。
- Ryzen 7 9700X（8コア / 16論理コア）、RAM 31,938 MB、RX 7800 XT、Windows 11 Build 26200。
- 現在MODなし。以前セーブで使用したMODは GORA UI+ のみとの回答。
- 各回 `clear_ticktask_timings` を実行。意図した期間は1911/3/1→4/1。所要秒数の記録なし。
- 再ロードを忘れ、4月を計測した可能性があるとの回答。期間は全条件で確認済みとは扱わない。
- DLC、Pop Consolidation、セーブのファイル名とSHA-256、UI/カメラ/描画条件の詳細は未記録。

HWiNFOには同名の「総 CPU 使用率」が2列あるため、列位置64をA、82をBとして別々に保管し、同一指標として合算していない（位置は0始まり）。列の意味の詳細は未確認。各平均は記録全区間の単純サンプル平均で、シミュレーション区間だけの平均ではない。

最高CPU温度は67.6℃。HTC/PROCHOT CPU/PROCHOT EXTは全126サンプルで「いいえ」。捕捉したサンプルでは熱スロットリングの申告はない。約2秒間隔の観測なので、サンプル間の瞬間的な状態までは保証しない。低い全コア平均実効クロックはアイドルも反映するため、それだけでブースト低下と判断しない。

論理コア別の負荷には偏りがあり、全体CPU使用率から「CPUに余裕があり処理速度も上げられる」と判断できない。Victoria3.exe単体のCPU時間、スレッド待ち、呼出しスタックはこのHWiNFOログでは確認できない。

## ゲームログの所見

- `game.log:95` ほか：MOD不足警告に GORA UI+ が表示される。ユーザー回答と一致するセーブの履歴として記録する。現在有効なMODがあるという証拠にはしない。
- `error.log` とローテーション済みログに `kates_power_bloc_rule_*` の未解決参照と `MISSING_DLC_ENTRY` が多数ある。ユーザーはGORA UI+以外の過去MOD使用を否定しているため、特定MOD由来とは断定しない。セーブ・DLC・ルール・バージョン互換性などの原因は未確認。
- 大量の参照エラーは保存されている時刻では08:32:42〜08:33:07に集中しており、08:32:50/08:33:16のロード完了記録周辺。ゲーム実行中に継続して同じ頻度で出ているとは確認できず、ログI/Oを性能低下原因とは断定できない。
- debugログのローテーション5本が08:33:05〜08:33:07付近のエラーで占められており、以前の計測のconsole記録が残っていない。「今回全体を採取した」ログでも、初期runのコマンドを後から検証できない状態。
- `debug.log:138-139`：08:34:03に7,676行のdump成功。12スレッドCSVの行数と一致。
- `debug.log:140-143`：08:34:20に122frameをclearし、08:34:24に16スレッド設定成功。
- `debug.log:144-148`：16スレッド設定後に1911年4月のイベントが出ている。
- `debug.log:149`：08:34:52に `building_livestock_ranch` のbacking building生成失敗assertion。クラッシュや停止の有無、その性能影響は未確認。
- 最新debugログは08:34:52で終わり、16スレッドのdump成功記録は収録されていない。HWiNFOは08:35:05まであるので、ログ末尾の欠落・書込みバッファ等も考慮する。

`longest_lock` の最大は2スレッドの `UpdateWorldMarket` の79ms。16スレッドでは `UpdateNationalAwakenings` 55ms、`UpdateBuildingSpendingPriorities_Stage2` 51msも見える。ただし列名だけでOS mutexの競合待ちや根本原因を確定しない。WPR/WPA等の待ち・CPUスタック記録が次の証拠になる。

## 追加で必要な情報と計測

最優先は同一セーブ・同一期日に対する実測秒数。今回の秒数をHWiNFO記録幅やclear→dumpの時間差から作り直して埋めることはしない。

1. 計測に使った1911/3/1のセーブ本体（またはファイル名とSHA-256）。DLCとPop Consolidationの設定も記録する。
2. 最初は8/12/16の3条件を、同じセーブを毎回読み直して比較。各条件でwarm-upを1回、記録する計測を3回行う。安定性が確認できたら1/2/4/6を追加する。
3. 毎回pause状態でスレッド設定・clearを済ませ、1911/3/1→4/1をSpeed 5で進める。unpauseと同時に実時間計測を開始し、4/1にpauseして所要秒数を保存。月境界を越えた場合はその回を別記する。
4. HWiNFOはゲーム計測の少し前から少し後まで記録してよいが、unpause/pauseの実時刻を別に残す。CSVは各回別名で保存する。
5. 現在のセーブのエラーについては、まずセーブ・設定から調査する。今回のデータを捨てたり、UI MOD履歴だけを理由に重いセーブを作り直したりする必要はない。
6. 大きな負荷の原因を確定するOS-level traceとScript/GUI profilerは次段階の診断資料。初回の追加データとして全部同時に取る必要はない。

## 方法と検証

- 入力ZIPのCRC整合性を検証し、含まれるCSVをすべて読み取った。
- 54,003行のTickTaskレコードに対し、必須列、有限・非負数、callsの整数性を検証。一意なframe/taskの重複なし。
- 7条件・1,770タスク集計を、GitHub mainから取得した `tools/analyze_benchmarks.py` の `load_ticktask_csv` と照合し、累計ms・calls・最大longest_lockの一致を確認。
- HWiNFOはUTF-8の見出しとCP932の「いいえ」が混在していた。該当セルだけを厳密にCP932で復元し、数値列を変更せず解析。繰り返し見出しと末尾のセンサー説明行を除外した。
- wall-clockの仮値や、根拠のない `vanilla` manifestは生成していない。
