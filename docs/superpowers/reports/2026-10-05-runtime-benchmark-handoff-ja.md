- 民間投資、人口成長、経済移民、雇用更新、修正値再計算が主要な調査候補。実測上位20件と longest_lock 上位20件をRTTI/vtableの対応箇所に照合済み。longest_lockをOSのmutex待ちと断定しない。
- 民間投資 `0xf6e590`、経済移民 `0x11b0c00`、雇用更新 `0x13b8310` の固有の入口と直接の呼出し先を調べた。入口はクラス固有の最終仮想関数であり、ソース上のExecuteや処理全体の範囲は未証明。
- 経済移民の最初の例外処理情報は10バイトだけ。連鎖をたどると3断片・478バイト、`0x11b0c00–0x11b0dde`。既存マッパーの最初の断片と、関数全体を混同しない。
- 現在の実行ファイルを読み取りのみで確認。既存の18シグネチャは期待位置で一意に一致。ゲーム本体・セーブ・ゲーム内設定は変更していない。性能変更やDLL実装・注入は未実施。

## iPad側から進められる作業

iPadからGitHubの資料を読む、新しいチャットへ引き継ぐ、接続されたクラウド実行環境でCSVを再集計する作業を進められる。GitHubに保存しただけで、このローカルチャットやWindows環境がiPadへ移動するわけではない。自動同期やクラウド実行環境の存在は確認していない。

1. 最新の3か月集計と対応表を読み、民間投資・経済移民・雇用更新の間接呼出し、処理オブジェクト、共通の呼出し先について未確定部分を整理する。保存済みの呼出し先だけでschedulerや待ちの原因を決めない。
2. `tools/map_ticktask_rtti.py` のRUNTIME_FUNCTION境界を使う箇所について、chained unwind情報を扱う改善を検討する。複数段連鎖・非連続断片・共有unwind情報・循環/不正参照の合成テストを先に作り、開始/終了/unwindの組で元の関数を区別する。既存の18シグネチャの位置はこの発見だけで変えない。
3. `tools/analyze_benchmarks.py` の単一観測に対する表示を確認する。CV=nullや標準偏差未算出を「ばらつき0」「noisy=falseだから安定」と扱わない。必要な表示改善は合成データで検証してから行う。
4. OS実測を受け取った時に照合する対象表を準備する。直接関数の所要時間だけで、子タスクの処理全体が測れるとは限らない。

これらは次の候補であり、この引き継ぎコミットで解析ツールを修正したという意味ではない。

## Windows実行環境が必要な作業

- 本体のさらに深い逆アセンブルや実行時の処理経路確認には、同じSHA-256の実行ファイルが必要。実行ファイルはこのリポジトリへ追加していない。
- 同じセーブ・1911/3/1→6/1・16スレッドで、CPUサンプル、スレッド待ち、context switchを含むWPR/WPA等の記録を取得し、対応表と照合する。必要に応じて12と比較する。既存の [OS計測計画](../../../research/os-profiling-plan.md) を参照。
- 最速設定とばらつきを確定するなら同じ3か月を8/12/16各3回測定。全条件や1スレッドからの取り直しを、構造調査の開始条件にしない。
- ネイティブ計測器は [hook方針](../../../research/hook-feasibility.md) と既存設計を確認し、対象・実行経路の証拠を得た後に進める。性能を変える処理回数・計算内容・schedulerの変更は根拠が揃ってから。

## 保存したデータと再集計

今回の3か月CSVは元バイトを保持して `benchmarks/measured-2026-10-05-3month/baseline-t08-r01/`、`baseline-t12-r01/`、`baseline-t16-r01/` に保存した。各フォルダに `manifest.json` と `ticktask_timings.csv` があり、元CSVのSHA-256を記録する。各条件の秒数はユーザーの提示値を入力し、ログ時刻から推定していない。

```text
python tools/analyze_benchmarks.py benchmarks/measured-2026-10-05-3month --json local-data/bench3-report.json
```

標準集計結果のnoisy=falseは単一観測から安定性を証明しない。日本語報告とこの資料の「各条件1回」という制約を併せて読む。
